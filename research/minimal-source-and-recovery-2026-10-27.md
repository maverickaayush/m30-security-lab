# Source compatibility and recovery decision (offline)

Checked against the running M305FDDS8CVB2 `/proc/config.gz`, live BOOT and `/proc/kallsyms`, exact INS stock AP, and public M30-family source revision `095206579f69121278ed1dd5fd0d7975c0705c6a`. No partition was written. Source search dates: 2026-10-27.

## Source gaps narrowed

The earlier 46-symbol report correctly identified differences but overstated missing source for several security paths. In the pinned family tree, `security/samsung/defex_lsm/Kconfig` defines `DEFEX_KERNEL_ONLY`; `drivers/soc/samsung/exynos-el3_mon.c` implements `EXYNOS_KERNEL_PROTECTION`; `drivers/misc/Kconfig` and arm64 page-table sites implement `KNOX_KAP`; `arch/arm64/Kconfig` defines TIMA; `security/tz_iccc` and `drivers/md/dm-verity-target.c` implement TZ_ICCC; and `drivers/crypto/fmp` contains the FMP/FIPS choice. The family defconfig disabled some of these, and its malformed `# CONFIG_TIMA isn ot set` left TIMA off, hiding `TZ_ICCC` despite a later request for it. The minimal fragment requests the live choices; the effective generated `.config` must be checked after Kconfig normalization.

The live kernel **does** have `FMM_LOCK_OFFSET=7340680` and `SEC_DEBUG_SOFTDOG_PWDT=y`, but neither symbol or its implementation appears in the pinned family tree. A serial-pinned, read-only `/proc/kallsyms` check of the exact live kernel showed `store_FMM_lock`, `sec_debug_fmm_lock_offset`, the setup handler, `dev_attr_FMM_lock` and `fmm_lock_offset`; addresses were redacted. This is direct runtime evidence that the FMM path is compiled into the installed kernel. Its secure-state/partition contract is not recovered, so inventing a Kconfig declaration would be misleading. Standard `SOFT_WATCHDOG` and its `softdog_*` symbols are present in both live and family source, but they do not explain the missing Samsung `SEC_DEBUG_SOFTDOG_PWDT` option. The two missing SCSC WLAN declarations are **n** on the phone, with no enabled path lost in the candidate.

The live `SECURITY_DEFEX` value is n, so `DEFEX_KERNEL_ONLY=y` is a mode flag rather than proof that active DEFEX enforcement is missing in the candidate. `EXYNOS_FMP=y` remains enabled, while live `EXYNOS_FMP_FIPS=n`; disabling the family-only FIPS self-test restores the observed choice. `TZ_ICCC` is more material: the family dm-verity error path can call `SMC_CMD_DMV_WRITE_STATUS` only when this option is active. `EXYNOS_KERNEL_PROTECTION` calls secure monitor code to protect kernel text. Compilation of these paths does not establish that the family's secure-world ABI matches the exact installed firmware.

Samsung [Open Source Release Center](https://opensource.samsung.com/uploadList?menuItem=mobile) is the authoritative place for corresponding source; the exact `SM-M305F` search/download endpoint was not retrievable through the available web interface. Public [M30 family source](https://github.com/akhil1999/android_kernel_samsung_m30lte/tree/095206579f69121278ed1dd5fd0d7975c0705c6a) is a buildable comparison, not the installed-build source. Search of the pinned tree and public web results found no matching implementation for the two enabled missing symbols. The next source step is to obtain the corresponding Samsung release or a demonstrably equivalent patch and compare its FMM/security/debug code, not to mask the delta.

## Backup and recovery state

The persistent host BOOT, DTB, DTBO and RECOVERY copies in ignored `backups/private-20261027/` are readable, mode 0600 in a mode 0700 directory, and their SHA-256 values still match the private manifest. A second hash pass of the phone's user-data copies also matched. The exact stock INS archive's locally computed SHA-256 still matches its acquisition record; all ZIP CRC and Samsung TAR MD5 checks were previously passed. These checks establish copy integrity, not restorability. There is no mounted external drive; the phone copy is on a separate physical device but shares failure modes with the handset being modified. The laptop has only about 160 MiB free on its persistent Linux filesystem; `/tmp` and `/dev/shm` build outputs are volatile. An independent external backup and more host space remain prudent before any boot trial.

The verified PIT maps BOOT to partition ID 12, size 32 MiB (`mmcblk0p12`), and RECOVERY to ID 13. Separate DTB and DTBO partitions are zero-filled and are not part of the proposed change. Heimdall 2.1.0 (`heimdall-flash` Ubuntu package SHA-256 `85e231101848e2a5f66697628092c2259f8379e8c4e36e6f9062312aa05bc90f`) was extracted project-locally and successfully parsed the **device-read PIT file offline**, confirming BOOT name, ID 12 and 65,536 512-byte sectors. Its `help flash` supports a named single-partition argument, so the prospective Download Mode rollback syntax is `heimdall flash --BOOT <verified-original-BOOT.img>` **only after live detection/PIT reconfirmation**. The tool was not run against the phone in this phase; its actual USB interoperability and flash operation remain untested. TWRP screen entry/return and prior Download Mode identification/PIT read were observed, but neither a TWRP restore nor a Download Mode flash has been tested. Do not interpret access to either mode as a verified restore.

**Planned one-partition rollback, not executed:** keep the exact current 32 MiB BOOT backup and its SHA-256, the stock AP package and the private PIT manifest accessible off-phone. If a future one-partition kernel trial fails, enter the already verified TWRP UI, transfer the original BOOT image, choose TWRP's Install Image flow and the **Boot** destination only, verify the selected filename/partition before swiping, then reboot to Android and check kernel identity, ADB, SELinux, storage and Bluetooth. The exact TWRP image-write behavior on this installed recovery remains untested. If recovery is inaccessible or rejects the image, use the previously verified Download Mode as the fallback: run Heimdall `detect` and `print-pit` first, require the same BOOT name/size/ID, verify original image hash, then use its named `flash --BOOT` operation. The host restore utility's live detection, flash operation and Samsung acceptance remain untested. A full stock package is available as a last-resort source of original components, but full AP/CSC flashing is outside this proposed single-partition trial and may affect Magisk or user data. No wipe, RECOVERY write, DTB/DTBO write, bootloader change or downgrade is part of this plan.

## Decision boundary

Preserving the live embedded DTBH and ramdisk removes the identified board-clock, camera-regulator and Magisk/verity deltas. The remaining source differences are specific, not a generic “source mismatch”: missing live FMM/debug hooks and unproven secure-world/driver ABI. Live symbols show the FMM path exists, but no evidence shows it is needed before Android mounts storage; the debug watchdog option may affect fault handling rather than ordinary boot. These are functional/security risks to measure during a controlled boot trial, not proof that the image cannot boot. A future controlled boot experiment is a justified way to test residual runtime uncertainty **once an independent external rollback copy and a concrete host restore utility/procedure are checked**. This investigation does not flash.
